## Critical Issues

### CR-01: Printed VAT rows can fail arithmetic (unrounded float tax/total)

**File:** `packages/pdf-templates/src/render-invoice.ts:142-169`
**Issue:** `taxAmount` and `total` are computed as raw floats (`subtotal * (rate / 100)`, `subtotal + taxAmount`) then each passed through `Intl.NumberFormat` independently. Half-cent cases produce **internally inconsistent** paper: e.g. net `45.50` @ 19% → tax amount `8.645` / total `54.1449…` formats as **45,50 € + 8,65 € ≠ 54,14 €** (correct commercial total is **54,15 €** after rounding tax to 2 dp). Legal invoice PDF must have additive totals.
**Fix:** Round to EUR cents before format (or compute in integer cents). Prefer: round tax first, then total = net + rounded tax.

```typescript
function roundEur(n: number): number {
  return Math.round((n + Number.EPSILON) * 100) / 100;
}

const subtotal = roundEur(
  model.items.reduce((sum, line) => sum + Number(line.netto), 0)
);
const rate = Number(tax.invoice_tax_rate) || 0;
const showTax = tax.invoice_tax_shown === true;
const taxAmount = showTax ? roundEur(subtotal * (rate / 100)) : 0;
const total = roundEur(subtotal + taxAmount);
```

Add a unit case for `45.50` @ 19% asserting formatted tax `8,65` and total `54,15` (de).

### WR-02: Nest input validation accepts non-finite numbers

**File:** `apps/backend/src/pdf/invoice-pdf.service.ts:56-71`
**Issue:** Checks `typeof … === "number"` only. `NaN` and `Infinity` pass (`typeof NaN === "number"`). In `render-invoice.ts:146`, `Number(tax.invoice_tax_rate) || 0` then collapses `NaN` to **0%** while `invoice_tax_shown` can still be true → PDF shows **MwSt 0 %** with magic bytes (fail-open on bad math). Same risk for line `netto` / `einzelpreis` → `formatMoney(NaN)` still yields `%PDF-`.
**Fix:** Reject non-finite values in `validateInput`:

```typescript
function isFiniteNumber(value: unknown): value is number {
  return typeof value === "number" && Number.isFinite(value);
}
// use for invoice_tax_rate, menge, einzelpreis, netto
```

Optionally mirror a light guard in `renderInvoice` for direct package callers.

### WR-03: Prisma `Decimal` line amounts will always fail Nest typeof gates

**File:** `apps/backend/src/pdf/invoice-pdf.service.ts:63-71` (call boundary)
**Issue:** Schema stores `menge` / `einzelpreis` / `netto` as `Decimal` (`apps/backend/prisma/schema.prisma:68-70`). `typeof decimal !== "number"`, so any Phase 5 caller that passes Prisma rows straight into `InvoicePdfService.render` gets `RenderFailedError` with no coercion. Fail-closed is correct; missing boundary conversion is an easy integration footgun right after this cutover.
**Fix:** Coerce at the service edge (or a tiny mapper used by future download route):

```typescript
const toNum = (v: unknown): number =>
  typeof v === "number" ? v : Number(String(v));
// after coerce, require Number.isFinite
```
