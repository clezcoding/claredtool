# Phase 04.7: Factur-X / ZUGFeRD / XRechnung e-invoice XML - Context

**Gathered:** 2026-09-05
**Status:** Ready for planning

<domain>
## Phase Boundary

On the Takumi+pdfcn engine from Phase 04.6, emit a **legal German/EU e-invoice**: EN 16931 **Comfort** CII embedded in PDF/A-3b (Factur-X/ZUGFeRD) plus a separate **XRechnung 3.x UBL** XML artifact. Visual totals must equal XML totals. Founder priority: **full EU/DE compliance**.

**In scope:**

1. `@clared/e-invoice` — shared EN 16931 facts model; CII serializer (Factur-X attachment) + UBL serializer (XRechnung); TaxDecision → VAT category mapping.
2. Same Nest render path: Takumi `pdfa: "3b"` + `attachments` (`factur-x.xml`) + Factur-X XMP. Takumi does **not** build XML. No pdf-lib / second embed pass. Library embed APIs forbidden.
3. Prisma + desktop: e-invoice stammdaten (structured address, optional IBAN/BIC on seller, Leitweg/Buyer-Ref on buyer, `unit` on lines, `supplyType` UI) by **extending** existing Entity/Customer/Invoice dialogs.
4. Single product render path: PDF/A-3b + embedded XML + XRechnung bytes when facts complete; fail-closed otherwise (no silent visual-only fallback).
5. CI: KoSIT and/or Mustang (local) blocking; broad fixture matrix (Research prioritizes from tax rules + EN 16931). Optional free online validators for Dev/UAT only.
6. Replace 04.6 visual-only fixtures with hybrid + XRechnung fixtures.

**Out of scope (non-negotiable):**

- PDF-01 desktop download/view, public generate HTTP, `issued` status UI (Phase 5)
- Artifact persistence / Garage provisioning (Phase 5 — Garage locked as store)
- Credit Note / Storno (later phase — full quality when built)
- Extended ZUGFeRD profile; PDF/UA-1; MINIMUM/BASIC WL profiles
- Logo upload (Phase 6); MAIL-01; Peppol send network

</domain>

<decisions>
## Implementation Decisions

### XRechnung & facts model
- **D-01:** Pure XRechnung artifact is **UBL Invoice**, target **XRechnung 3.x** (exact patch via Research). Factur-X attachment remains **CII**. — **Reversibility:** costly — dual serializers and CI validators keyed to UBL vs CII.
- **D-02:** One shared **EN 16931 facts model**; two serializers (CII + UBL). No dual mappers from InvoiceModel; no CII→UBL converter chain.
- **D-03:** Every successful e-invoice render produces **both** hybrid PDF bytes and XRechnung XML bytes (fixtures + internal service). No runtime flag in 4.7.

### XML library & package
- **D-04:** First candidate **`node-zugferd` for XML only** (`toXML` / equivalent). Research must prove Comfort + validatable output. If insufficient → Research picks replacement; **never** downgrade to MINIMUM/BASIC. — **Reversibility:** costly — package API shapes fixtures.
- **D-05:** Code lives in workspace package **`@clared/e-invoice`** (analog `@clared/tax-engine`), not inside `pdf-templates`.
- **D-06:** Embed **only** via Takumi `pdfa: "3b"` + `attachments` + XMP. Library must not embed into PDF.

### Profile, filename, layout
- **D-07:** ZUGFeRD/Factur-X profile = **EN 16931 Comfort only**. Extended deferred.
- **D-08:** Research pins concrete current reproducible Spec versions for CI (ZUGFeRD/Factur-X + XRechnung 3.x).
- **D-09:** Attachment filename **`factur-x.xml`** (ROADMAP / Takumi docs).
- **D-10:** Visual layout = pdfcn **Invoice Minimal** + Crafted Minimal from 04.6; only add PDF/A-3b + XML packaging.

### Fail-closed & single path
- **D-11:** Missing mandatory e-invoice fields → **fail-closed** (no PDF, no XML). No PII in exception messages (extends 04.6 D-26).
- **D-12:** Incomplete stammdaten must **not** fall back to visual-only PDF. One product path: hybrid + XRechnung or error. — **Reversibility:** one-way for callers expecting 04.6 visual-only success.
- **D-13:** Replace 04.6 visual-only fixtures; hybrid + XRechnung only.

### Schema & desktop stammdaten
- **D-14:** 4.7 includes **Prisma schema + desktop forms** for e-invoice fields (founder expanded beyond “bytes only”). — **Reversibility:** costly — migrations + UI.
- **D-15:** Extend existing **Entity** and **Customer** dialogs (and invoice fields as needed). No separate “E-Rechnung settings” page. No generate/download button in 4.7.
- **D-16:** **Seller (Entity):** structured address; optional IBAN/BIC; HRB/GF/Handelsregister if Research requires for Comfort. **Buyer (Customer):** structured address; optional Leitweg-ID + Buyer-Reference. **Invoice:** number/date/due/`supplyType`; Leitweg not duplicated on invoice by default.
- **D-17:** Form: sensible required fields (structured address, EU VAT where applicable). IBAN/Leitweg optional to save; **generate** fail-closed when required for that document.
- **D-18:** IBAN optional in facts; fixture may use test IBAN; **no fake IBAN** on live path.
- **D-19:** Leitweg in facts; **B2G fixture must include Leitweg**; B2B fixtures OK without; missing Leitweg ⇒ not B2G-OK.

### Address
- **D-20:** Structured address: street, postal code, city (+ existing country); optional `addressLine2`. Same structure for Entity and Customer. — **Reversibility:** costly — replaces free-text `address`.
- **D-21:** No legacy free-text parse migration (no real prod data; test DB reseed/edit OK). Incomplete structure = fail-closed like other mandatory fields.

### Draft / issued
- **D-22:** Engine runs only when **mandatory facts complete**. Fixtures are issued-looking (number/date/due; no ENTWURF watermark — 04.6 D-17).
- **D-23:** No `issued` status / “Stellen” UI in 4.7 — Phase 5 with download.

### Tax codes
- **D-24:** Map `TaxDecision` → EN 16931 VAT category codes inside **`@clared/e-invoice`**. Tax-engine package unchanged.
- **D-25:** Unknown tax combination → fail-closed (no guess to `S`/19%).
- **D-26:** Minimum mapping: standard 19% **and** reverse charge; further cases follow Research-prioritized fixture matrix from tax rules.

### Validation
- **D-27:** **CI blocks** on KoSIT and/or Mustang (local) — at least one official validator per artifact type; ideally both. Schematron/CIUS > XSD-only.
- **D-28:** Runtime Nest: schema + amount checks + fail-closed. **No** JVM KoSIT/Mustang on the request path.
- **D-29:** Free **online** validators (e.g. Facturwise) allowed for **Dev/UAT only** — not sole CI gate; **no production PII** uploads (fixtures/anonymous only).

### Units, supply type, i18n
- **D-30:** Line item **`unit` dropdown** in 4.7 (UNECE codes; start set via Research). List expandable later. Unknown code → **fallback Stück `C62`** (founder exception to general fail-closed).
- **D-31:** Map invoice `supplyType` into XML; unknown → fail-closed. Desktop UI for goods vs service on the invoice. **Mixed** goods+services on one invoice → **reject** with clear user-facing error (not per-line mix in 4.7).
- **D-32:** New form labels and user errors: **DE + EN** i18n. No PII in errors. XML normative codes; human-readable note text follows invoice `locale` knobs (like PDF), not desktop UI language.

### Persistence (explicit non-goals for 4.7)
- **D-33:** Do **not** persist PDF/XML in 4.7 — generate only (service + fixtures).
- **D-34:** Phase 5 direction (deferred): on Generate, persist hybrid PDF + XRechnung in **Garage** (existing Coolify S3-compatible stack; **not MinIO**).

### Claude's Discretion
- Exact Comfort BT field checklist and which seller legal fields (HRB/GF) are mandatory vs optional after Research.
- Initial UNECE unit dropdown set (beyond Stück/hour/common).
- Whether Mustang, KoSIT, or both land in which CI jobs; how online validators are documented for humans.
- Exact `node-zugferd` pin or replacement package after legitimacy research.
- How free-text `address` column is migrated in Prisma (drop vs keep unused) given no real legacy data.

</decisions>
