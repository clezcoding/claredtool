## Common Pitfalls

### Pitfall 1: XMP ConformanceLevel wrong string
**What goes wrong:** Mustang error 12 (invalid ConformanceLevel) or profile mismatch.
**Why it happens:** Takumi sample `profile.toUpperCase()` turns `en16931` into `EN16931`; Comfort alias confuses with Order-X `COMFORT`.
**How to avoid:** Hardcode `ConformanceLevel: "EN 16931"`; DocumentFileName `factur-x.xml`; DocumentType `INVOICE`; Version `1.0` (matches node-zugferd profile metadata).
**Warning signs:** Mustang validates XML but fails PDF XMP section.

### Pitfall 2: Visual totals ≠ XML totals
**What goes wrong:** Legal mismatch; Mustang arithmetical unreproducibility (error type 10).
**Why it happens:** Separate rounding paths; tax shown vs AE 0%; locale formatting vs numeric XML.
**How to avoid:** Share `roundEur` logic; compute money once in facts; assert PDF money inputs === XML amounts before render.
**Warning signs:** Fixture PDF shows 54,15 but XML has 54.14.

### Pitfall 3: XRechnung CIUS fields missing on UBL
**What goes wrong:** KoSIT / Mustang notices become errors for XRechnung (BT-10 Buyer reference, BG-6 Seller contact, BT-24 customization ID).
**Why it happens:** Comfort Factur-X B2B fixtures omit B2G-only fields; UBL path still needs XRechnung CIUS rules.
**How to avoid:** B2G fixture includes Leitweg in BT-10; add seller contact email/phone fields if Schematron requires BG-6 (recommend optional Prisma columns `sellerEmail`/`sellerPhone` or reuse future Entity contact — **confirm in Wave 0 with KoSIT on first UBL sample**). BT-24 = `urn:cen.eu:en16931:2017#compliant#urn:xeinkauf.de:kosit:xrechnung_3.0`.
**Warning signs:** BR-DE-15 / BR-DE-2 / BR-DE-21 in validator output.

### Pitfall 4: Java 8 locally / missing Java in CI
**What goes wrong:** Mustang fails to run; false green if job skipped.
**Why it happens:** Dev machine OpenJDK 8; Mustang requires JRE 11+.
**How to avoid:** GHA `setup-java` Temurin 17; document local SDKman/Temurin 17+; fail the CI job if validate step skipped.
**Warning signs:** `UnsupportedClassVersionError` or silent missing step.

### Pitfall 5: Transitive pdf-lib / embed API leak
**What goes wrong:** Accidental second embed; deny-list / security review fails.
**Why it happens:** `node-zugferd` depends on `pdf-lib` and exports `embedInPdf`.
**How to avoid:** Lint/test forbid `embedInPdf` imports; Nest deny-list if 04.6 pattern exists; only import `zugferd` + `profile/en16931`.
**Warning signs:** Bundle includes PDF mutation on request path.

### Pitfall 6: Tax rules rate 20 vs DE fixture 19
**What goes wrong:** Mapping tests assume rule JSON rates.
**Why it happens:** Exemplar `EU_DOMESTIC_B2B_SERVICE` uses AT/20% placeholder, not DE 19% [VERIFIED: `packages/tax-engine/rules/EU_DOMESTIC_B2B_SERVICE.json` `invoice_tax_rate: 20`].
**How to avoid:** Fixtures continue hardcoding DE TaxDecision shapes (as 04.6); map on decision fields, not rule_id alone.
**Warning signs:** Fixture expects 19% but evaluate() returns 20.

## Comfort / Stammdaten Field Guidance (Discretion)

**Mandatory for generate (fail-closed):**
- Seller/Buyer: name; street (`BT-35`/`BT-50` line 1); postal code; city; country
- Invoice: number; issue date; due date; currency; type code `380`; `supplyType` ∈ {`goods`,`service`} (Prisma already defaults `service` [VERIFIED: `schema.prisma:51`])
- Lines: name; quantity; unit (default `C62`); net price; line net; VAT category
- Tax: mapped category + totals; RC requires buyer+seller VAT IDs + exemption reason text

**Optional to save; may be required on generate for some docs:**
- IBAN/BIC (payment means) — fixture OK with test IBAN; live omit if empty
- Leitweg / Buyer reference — required for B2G fixture (D-19); typically BT-10
- HRB / GF — optional UI; include in GmbH fixture
- Seller email/phone — **likely required for XRechnung** (see Open Question 1)

**Initial UNECE unit dropdown (D-30):**
`C62` (Stück), `HUR` (hour), `DAY`, `MON`, `KGM`, `MTR`, `H87` (piece) — unknown → `C62`.

**`supplyType` in XML (D-31):** Reject mixed; map `goods` vs `service` into facts used by VAT category selection and a single invoice note / description convention; do not invent unsupported CII elements.
