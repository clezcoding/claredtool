## Critical Issues

### CR-01: Gotenberg ready probe omits Basic auth (BLOCKER)

**File:** `apps/backend/src/health/health.controller.ts:36-50` (producer); `.github/scripts/coolify-deploy-nest.sh:167-186` (consumer)
**Issue:** `ready()` GETs `${GOTENBERG_URL}/health` with no `Authorization` header. Convert path in `apps/backend/src/pdf/gotenberg.client.ts` requires `GOTENBERG_API_BASIC_AUTH_USERNAME` / `PASSWORD` on every call. Phase 04.3 closed Gotenberg WAN exposure with API Basic Auth (`T-04.3-04`); Coolify API/worker carry those env names. Gotenberg 8 with API auth rejects unauthenticated routes, including `/health`, with HTTP 401.

After this image ships: Coolify marks the deployment finished → poll requires HTTP 200 plus `.details.build.sha == SHA_TAG` → Terminus fails the Gotenberg indicator → `/health/ready` is 503 → `poll_ok` stays 0 → `rollback_changed` restores `PREV_API`. First pin of this image cannot stay live. Live `/health/ready` today still looks healthy only because the running image does not include this probe.

**Fix:** Send the same Basic auth as convert. Fail the indicator if auth env is missing while `GOTENBERG_URL` is set. Do not treat 401 as “up”.

```typescript
async (): Promise<HealthIndicatorResult> => {
  const raw = process.env.GOTENBERG_URL?.trim();
  if (!raw) {
    return { gotenberg: { status: "up", message: "skipped (GOTENBERG_URL unset)" } };
  }
  const user = process.env.GOTENBERG_API_BASIC_AUTH_USERNAME?.trim();
  const password = process.env.GOTENBERG_API_BASIC_AUTH_PASSWORD?.trim();
  if (!user || !password) {
    throw new Error("Gotenberg health: basic auth env missing");
  }
  const origin = raw.replace(/\/$/, "");
  const res = await fetch(`${origin}/health`, {
    headers: {
      Authorization: `Basic ${Buffer.from(`${user}:${password}`, "utf8").toString("base64")}`,
    },
    signal: AbortSignal.timeout(2_000),
  });
  if (!res.ok) {
    throw new Error(`Gotenberg health HTTP ${res.status}`);
  }
  return { gotenberg: { status: "up" } };
}
```

Prefer extracting a shared `gotenbergAuthHeader()` used by both convert and health so the two paths cannot drift again.

**File:** `.github/scripts/coolify-deploy-nest.sh:167-172`; `apps/backend/src/health/health.controller.ts:22-51`
**Issue:** Even after CR-01, post-deploy verification still requires HTTP 200 from full `/health/ready` (postgres + redis + **gotenberg** + build sha). }

### WR-02: Coolify and health curl calls have no timeouts

**File:** `.github/scripts/coolify-deploy-nest.sh:16-48`, `167-168`
**Issue:** `coolify_get`, `coolify_pin`, deployment polling, and the public health curl omit `--connect-timeout` / `--max-time`. `redis.ping()` in `ready()` is also unbounded. A hung Coolify API, stuck TLS handshake, or stalled Redis ping blocks until the deploy job `timeout-minutes: 30`, then relies on TERM→EXIT rollback. That stretches the half-pinned window.
**Fix:** Time-box every curl; keep POST `/deploy` well under the job timeout:

```bash
curl -fsS --connect-timeout 5 --max-time 30 -X GET \
  "${COOLIFY_URL}/api/v1/applications/${1}" \
  -H "Authorization: Bearer ${COOLIFY_TOKEN}" \
  -H "Accept: application/json"

curl -sS --connect-timeout 5 --max-time 15 -w "\n%{http_code}" \
  "https://clared-api.puzzlessdev.online/health/ready"
```

Add a timeout around `this.redis.ping()` (or Terminus redis indicator with timeout) so `/health/ready` cannot hang the poller.

### WR-03: Cancel / EXIT rollback path is untested

**File:** `.github/scripts/coolify-deploy-nest.test.sh:175-229`
**Issue:** Mock suite covers `health_fail`, `worker_deploy_fail`, and `success` only. `rollback_on_exit` plus INT/TERM→`exit` handlers exist so GHA cancel/timeout does not leave a half-pin. That path has no assertion. Dropping the EXIT trap or the `deploy_succeeded` guard still leaves CI green.
**Fix:** After the API pin stub appears in `PIN_LOG`, `kill -TERM` the deploy script and assert `pin:${API_UUID}:prev-api` plus non-zero exit. Keep `sleep` stubbed so the test does not wait on real backoff.

### WR-04: Parallel push jobs share one GHA cache scope

**File:** `.github/workflows/backend-image.yml:145-146`, `214-215`
**Issue:** REL-04 runs `push-api` and `push-worker` in parallel. Both use `cache-from`/`cache-to` `type=gha,scope=clared-backend,mode=max`. Two writers on one Buildx GHA cache scope race: flaky export, poisoned cache, or a failed push that still leaves a partial tag. Distinct cancel groups (lines 81-83 / 152-154) do not isolate cache.
**Fix:** Split scopes; keep a shared `cache-from` if desired:

```yaml
# push-api
cache-from: type=gha,scope=clared-backend-api
cache-to: type=gha,scope=clared-backend-api,mode=max

# push-worker
cache-from: type=gha,scope=clared-backend-worker
cache-to: type=gha,scope=clared-backend-worker,mode=max
```
