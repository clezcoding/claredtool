## Warnings

### WR-01: Worker poll accepts bare `running` without health proof

**File:** `.github/scripts/coolify-deploy-nest.sh:184-187`
**Issue:** Worker success treats `running` the same as `running:healthy`. The `HEALTH_ENABLED` guard applies only to `running:unknown`. If Coolify health checks are later enabled on the worker, a transitional or degraded `running` status could pass verification without a healthy signal.
**Fix:** When `HEALTH_ENABLED` is `true`, require `running:healthy` (or explicit healthy sub-status); keep the current `running` / `running:unknown` branches only when health checks are off.

```bash
case "$STATUS_LC" in
  running:healthy)
    poll_ok=1
    break
    ;;
  running)
    if [ "$HEALTH_ENABLED" != "true" ]; then
      poll_ok=1
      break
    fi
    ;;
  running:unknown)
    if [ "$HEALTH_ENABLED" != "true" ]; then
      poll_ok=1
      break
    fi
    ;;
esac
```

### WR-02: API health gate can pass before new container serves traffic

**File:** `.github/scripts/coolify-deploy-nest.sh:140-150`
**Issue:** Post-deploy verification requires Coolify metadata tag `LIVE_TAG == SHA_TAG` and `GET /health/ready == 200`. Coolify can update `docker_registry_image_tag` before the new container is live; an old healthy pod can satisfy both checks during a brief window, letting worker deploy proceed on a not-yet-verified API rollout.
**Fix:** Add a version-bearing readiness check (e.g. expose git SHA in `/health/ready` and assert it matches `SHA_TAG`), or poll until consecutive successful probes after tag match. Document accepted risk if Coolify restart is atomic enough in practice.
