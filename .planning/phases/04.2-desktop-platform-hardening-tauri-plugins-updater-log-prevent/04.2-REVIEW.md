## Warnings

### WR-01: `scrubSentryEvent` leaves top-level message and exception values unscrubbed

**File:** `apps/desktop/src/lib/sentry.ts:67-91`  
**Issue:** `scrubSentryEvent` spreads the original event then overwrites only `request`, `extra`, `user`, and `breadcrumbs`. Unhandled errors and `captureException` payloads keep `message`, `exception.values[].value`, `contexts`, and `tags` verbatim. Customer names or emails in thrown error text bypass D-40 scrubbing even though nested `extra`/`breadcrumbs` are handled.

**Fix:**
```typescript
export function scrubSentryEvent(event: SentryEvent): SentryEvent {
  const scrubbed = { ...event };
  // existing request/extra/user/breadcrumbs scrubbing …
  if (typeof scrubbed.message === "string") {
    scrubbed.message = redactMessage(scrubbed.message);
  }
  if (Array.isArray(scrubbed.exception?.values)) {
    scrubbed.exception = {
      ...scrubbed.exception,
      values: scrubbed.exception.values.map((v) =>
        typeof v?.value === "string"
          ? { ...v, value: redactMessage(v.value) }
          : v,
      ),
    };
  }
  return scrubbed;
}
```
Extend `SentryEvent` type and add tests for exception/message scrub paths.

### WR-02: Ready-state update dialog close button is a no-op

**File:** `apps/desktop/src/components/update-dialog.tsx:203-213`, `apps/desktop/src/components/update-dialog.tsx:230-233`  
**Issue:** Dialog `open` is controlled by updater state (`ready` keeps `open` true). `showCloseButton` is enabled for `ready`, but `handleOpenChange` only calls `dismissUpdate()` for `available` and `error`. Clicking X fires `onOpenChange(false)` without changing updater state; next render `open` stays true and the dialog cannot be dismissed except via "Später neu starten".

**Fix:**
```typescript
const handleOpenChange = (nextOpen: boolean) => {
  if (!nextOpen && (state === "available" || state === "error" || state === "ready")) {
    dismissUpdate();
  }
};
```
Alternatively set `showCloseButton={state === "available" || state === "error"}`.

### WR-03: Rust Sentry plugin has no PII scrub hook

**File:** `apps/desktop/src-tauri/src/lib.rs:231-250`  
**Issue:** JS `beforeSend` implements D-40 scrubbing, but the Rust `sentry::init` path only sets `send_default_pii = false`. Native panics, plugin-log forwarding, or Rust-layer captures can still ship tokens or session-related strings without the JS scrub pipeline.

**Fix:** Add a Rust `before_send` callback mirroring key redaction rules (Authorization drop, token-key redact, email regex), or document Rust captures as out-of-scope for D-40 and ensure no PII-bearing data reaches the Rust client.

## Info

### IN-01: `dismissUpdate` from `ready` resets state and clears `pluginUpdate`

**File:** `apps/desktop/src/lib/updater.ts:214-218`, `apps/desktop/src/components/update-dialog.tsx:294-299`  
**Issue:** "Später neu starten" calls `dismissUpdate()`, setting `idle` and nulling `pluginUpdate` while the staged update remains on disk. A subsequent check can surface `available` again and trigger a second `download`/`install` cycle until relaunch. Likely harmless (plugin may no-op or error) but noisy UX.

**Fix:** Track an `installedPendingRelaunch` flag instead of resetting to `idle`, or skip `check()` promotion when the same version was already installed this session.

### IN-02: No automated test for `ready`-state check guard

**File:** `apps/desktop/src/lib/updater.test.ts`  
**Issue:** WR-01 fix added `state === "ready"` short-circuit in `checkForUpdates` and UI disables, but only the `downloading` guard has a regression test. Ready-state guard could regress silently.

**Fix:** Add test: after `downloadUpdate()` reaches `ready`, assert `checkForUpdates(true)` does not call `check()` and returns existing `info`.
