## Warnings

### WR-01: Worker Coolify status glob treats `running: unhealthy` as success

**File:** `.github/workflows/backend-image.yml:325-330`
**Issue:** Poll uses `case "$STATUS_LC" in *running*)`. Coolify often returns `running: unhealthy` / `running: starting`. Both contain `running`, so a crashed or not-ready worker still sets `poll_ok=1`, skips rollback, and the deploy job succeeds. Origin 7ia text said “contains running”; collapsing the matrix kept that footgun. Plan 06 asked for status `running` only.
**Fix:** Match healthy running explicitly; reject `unhealthy`:

```bash
STATUS_LC=$(printf '%s' "$STATUS" | tr '[:upper:]' '[:lower:]' | tr -d ' ')
case "$STATUS_LC" in
  running|running:healthy)
    poll_ok=1
    break
    ;;
esac
```

### WR-02: API `/health/ready` poll can succeed on the previous revision

**File:** `.github/workflows/backend-image.yml:300-313`
**Issue:** After PATCH+POST, the script polls the public URL until HTTP 200. It does not check that Coolify finished swapping, nor that the live process matches `SHA_TAG`. If the old API container still answers 200 during overlap, the job proceeds to worker deploy. A later swap onto a broken new image is then outside the trap.
**Fix:** Prefer Coolify application status for API as well (same healthy-running check as WR-01), or poll until `docker_registry_image_tag` equals `SHA_TAG` *and* `/health/ready` is 200. Do not treat a 200 from an unspecified revision as “new API is live.”

### WR-03: Leftover `type=ref,event=branch` can publish a `:latest`-shaped GHCR tag

**File:** `.github/workflows/backend-image.yml:82-84`
**Issue:** D-24 dropped `type=raw,value=latest`. Metadata still has `type=ref,event=branch,enable=${{ github.ref != 'refs/heads/main' }}`. `workflow_dispatch` is not limited to `main`; the `build` job always `push: true`. Dispatch from a branch named `latest` publishes `ghcr.io/<repo>:latest`, which reopens the “mutable latest pointer” the phase removed. Same path publishes arbitrary branch tags into the production registry (deploy stays on `main`, push does not).
**Fix:** Delete the `type=ref,event=branch` line so tags are SHA-only. Optionally add `if: github.ref == 'refs/heads/main'` on `build` so dispatch from feature branches cannot push.

```yaml
tags: |
  type=sha,prefix=sha-,format=short
```

### WR-04: FaynoSync upload treats HTTP ≥400 as success if the body contains `already exists`

**File:** `.github/workflows/desktop-build.yml:274` and `:321`
**Issue:** `test "$HTTP_CODE" -lt 400 || grep -q 'already exists' /tmp/fayno-mac.json` (same for Windows). A 500/502 HTML or JSON error that happens to include the substring `already exists` passes. Duplicate-version handling should be an exact 409 (or documented success code), not a body substring.
**Fix:**

```bash
if [ "$HTTP_CODE" -lt 400 ]; then
  :
elif [ "$HTTP_CODE" = "409" ] && grep -q 'already exists' /tmp/fayno-mac.json; then
  :
else
  echo "FaynoSync upload failed HTTP ${HTTP_CODE}"
  exit 1
fi
```

## Info

### IN-01: `${{ }}` still interpolated inside `run:` on signed desktop

**File:** `.github/workflows/desktop-build.yml:69` and `:198`
**Issue:** Plan 07 claimed env-wrap. `Resolve build environment` and `Resolve FaynoSync base URL` still expand a ternary in the shell. The result is only `staging` / `production` / choice `inputs.target` (not a raw tag or PR title), and the workflow is not PR-triggered — not an external injection. Still the pattern zizmor env-wrap exists to avoid.
**Fix:** Assign the ternary to `env:` and quote `"$TARGET"` / `"$FS_ENV"` in the script (same as the step-summary block).

### IN-02: Analysis workflows omit Harden-Runner

**File:** `.github/workflows/gitleaks.yml:24`, `.github/workflows/zizmor.yml:39`, `.github/workflows/codeql.yml:56`
**Issue:** `ci.yml` / `desktop-build.yml` / `backend-image.yml` start with `step-security/harden-runner` (`egress-policy: audit`). Gitleaks, Zizmor, and CodeQL do not. No extra secrets on those jobs; inconsistency only.
**Fix:** Add the same SHA-pinned Harden-Runner step first if the founder wants uniform audit coverage.

### IN-03: `cosign-installer` downloads Cosign `v3.0.6` at runtime

**File:** `.github/workflows/backend-image.yml:172-174`
**Issue:** Installer action is SHA-pinned; `cosign-release: v3.0.6` still fetches a GitHub Release blob. Privileged job (`packages: write`, `id-token: write`). Residual installer class, not tag-mutation of the action itself.
**Fix:** Pin a verified checksum if the installer supports it, or vendor the binary.

### IN-04: `rust-toolchain.toml` triggers CodeQL but does not enable Rust analyze

**File:** `.github/workflows/codeql.yml:18` vs `:74-78`
**Issue:** Workflow `on.push`/`pull_request` paths include `rust-toolchain.toml`. `detect` rust filter does not. A toolchain-only PR starts the workflow, sets both language outputs false, and skips analyze.
**Fix:** Add `rust-toolchain.toml` to the rust paths-filter (and keep it on workflow paths).

### IN-05: FaynoSync response bodies are echoed to workflow logs

**File:** `.github/workflows/desktop-build.yml:273` and `:320`
**Issue:** `cat /tmp/fayno-mac.json` / `fayno-win.json` after upload. GitHub masks the raw `FAYNOSYNC_CI_TOKEN`; derived fields in the JSON may not be. Token stays in `Authorization` header, not the form `data` payload — low residual.
**Fix:** Log HTTP code + a jq projection (`version`, `id`) instead of the raw body.
