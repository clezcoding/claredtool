## Summary

Full-phase adversarial pass across PDF/Gotenberg/BullMQ worker, OTel/Pino, CI/Docker, desktop offline prep (SQLCipher, capabilities, debug panel), and compose. Prior scoped auto-fix loop (otel, worker shutdown, build.rs) looks sound — no regressions there.

No ship-blocking security or data-loss defects found in this pass; six warnings should be addressed before heavy PDF traffic or multi-replica API deploys.

## Warnings

### WR-01: Poison-queue jobs may retry on validation errors

**File:** `apps/backend/src/pdf/pdf.processor.ts:9-12`
**Issue:** `EmptyHtmlError` is thrown for invalid job payloads inside the worker. BullMQ treats thrown errors as transient failures unless marked unrecoverable; without explicit `UnrecoverableError` (or `attempts: 1` + `removeOnFail`), malformed jobs can sit in the retry/backoff cycle and waste worker capacity.
**Fix:** Import and throw `UnrecoverableError` from `bullmq` for validation failures:

```typescript
import { UnrecoverableError } from "bullmq";

if (typeof job.data?.html !== "string" || !job.data.html.trim()) {
  throw new UnrecoverableError("html must be non-empty");
}
```

Mirror the same pattern anywhere `EmptyHtmlError` is thrown from the processor path.

### WR-02: Gotenberg success responses are not validated as PDF

**File:** `apps/backend/src/pdf/gotenberg.client.ts:49-53`
**Issue:** Any HTTP 2xx body is returned as `{ contentType: "application/pdf" }` without checking magic bytes (`%PDF-`) or minimum size. Gotenberg misconfiguration or Chromium error pages returned as 200 would propagate garbage downstream in Phase 5.
**Fix:** After `arrayBuffer()`, reject non-PDF payloads:

```typescript
const bytes = new Uint8Array(await res.arrayBuffer());
if (bytes.byteLength < 5 || String.fromCharCode(...bytes.slice(0, 4)) !== "%PDF") {
  throw new Error("Gotenberg response is not a PDF");
}
return { bytes, contentType: "application/pdf" };
```

### WR-03: PDF queue jobs have no retention policy

**File:** `apps/backend/src/pdf/pdf.service.ts:15`
**Issue:** `queue.add` sets only `jobId`; no `removeOnComplete` / `removeOnFail` / TTL. Completed and failed PDF jobs accumulate in Redis indefinitely once enqueue starts in production.
**Fix:** Add explicit retention on enqueue or via `defaultJobOptions` on `BullModule.registerQueue`:

```typescript
return this.queue.add(
  "html",
  { html: facts.html },
  {
    jobId: crypto.randomUUID(),
    removeOnComplete: { age: 86_400 },
    removeOnFail: { age: 604_800 },
  },
);
```

### WR-04: Worker SIGTERM handler can leave an unhandled rejection

**File:** `apps/backend/src/worker.ts:14-19`
**Issue:** `shutdown()` awaits `app.close()` but has no `try/catch`. If Nest/BullMQ teardown throws, the promise rejects with no handler and the process may hang until SIGKILL — in-flight PDF jobs can be dropped mid-flight without a logged failure.
**Fix:**

```typescript
const shutdown = async (signal: string) => {
  try {
    await app.close();
    process.exit(0);
  } catch (err) {
    console.error(`${signal} shutdown failed`, err);
    process.exit(1);
  }
};
process.on("SIGTERM", () => void shutdown("SIGTERM"));
process.on("SIGINT", () => void shutdown("SIGINT"));
```

### WR-05: Node.js runtime version drift between CI and Docker

**File:** `.github/workflows/ci.yml:59` and `apps/backend/Dockerfile:1`
**Issue:** CI runs Node 26; production images use `node:22-bookworm-slim`. `File`, `AbortSignal.timeout`, and `crypto.randomUUID` behave the same today, but subtle stdlib or OpenSSL differences can slip through CI undetected.
**Fix:** Align versions — either bump Dockerfile to `node:26-bookworm-slim` or pin CI to Node 22 to match the deploy artifact.

### WR-06: Rust unit tests for Sentry scrubbing are not in CI

**File:** `.github/workflows/ci.yml:66-86` and `apps/desktop/src-tauri/src/lib.rs:690-707`
**Issue:** `sentry_scrub_tests` in `lib.rs` cover customer-name and email redaction, but `desktop-test` only runs Vitest. A regression in `sentry_redact_message` would not fail CI.
**Fix:** Add a job step (or separate job) before/after desktop tests:

```yaml
- run: cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml sentry_scrub
```

## Info

### IN-01: Compose worker build omits Dockerfile `worker` target

**File:** `compose.clared.yml:38-42`
**Issue:** Local worker service builds the default final stage (`api`) and overrides `command`. Works today because both stages share the same `build` filesystem, but diverging stage contents later could silently break local worker runs.
**Fix:** Add `target: worker` under `build` for clarity and parity with `backend-image.yml`.

### IN-02: API readiness does not cover Gotenberg or PDF worker path

**File:** `apps/backend/src/health/health.controller.ts:25-32`
**Issue:** `/health/ready` checks Postgres and Redis only. A dead Gotenberg or stopped worker process still reports API ready — Uptime Kuma may cover this externally, but the Nest health contract does not reflect PDF pipeline availability.
**Fix:** Defer until Phase 5 if intentional; otherwise add optional Gotenberg ping and/or BullMQ queue depth indicator behind a feature flag.

### IN-03: Release capabilities grant fs/dialog/sharekit to main window

**File:** `apps/desktop/src-tauri/capabilities/default.json:23-37`
**Issue:** D-33 scopes *smokes* to the debug panel, but release `default.json` already exposes fs write, dialog, and sharekit to `main`. Acceptable for Phase 5 prep; slightly wider blast radius than debug-only caps (sql correctly stays in `debug.json`).
**Fix:** No change required for 4.3 if intentional; tighten to `debug.json` before shipping offline product flows if you want defense-in-depth.

### IN-04: Prisma migrate runs on every API container start

**File:** `apps/backend/Dockerfile:46`
**Issue:** `prisma migrate deploy` in the API `CMD` races when multiple replicas start concurrently. Single-replica Coolify deploy is fine; horizontal scale needs external migration orchestration.
**Fix:** Document single-replica migrate expectation or run migrations as a one-shot init container / deploy hook.
